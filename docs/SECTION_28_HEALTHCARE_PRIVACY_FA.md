# بخش ۲۸ — حفاظت از داده پزشکی و حریم خصوصی (پیاده‌سازی مرحله اول)

**وضعیت:** کد ثبت و بازبینی درخواست حقوق داده روی شاخه `feature/section-28-healthcare-privacy` افزوده شد؛ **نه تأیید تولیدی و نه انطباق با GDPR/HIPAA/ISO**. هرگونه استفاده از داده بیمار واقعی تا بررسی مستقل امنیت، قراردادها، هویت، زیرساخت و الزامات حقوقی بازار مقصد ممنوع است.

## کنترل‌های موجود از بخش‌های قبل
- JWT، چرخش Refresh، تفکیک سطح دسترسی، MFA اختیاری کارکنان، تفکیک Tenant و Audit پایه
- رضایت هدف‌محور و قابلیت لغو، فایل خصوصی رمزنگاری‌شده محیط توسعه و آداپتور S3/KMS/ClamAV مشروط به تأیید
- محدودسازی تلاش ورود، ورودی‌های اعتبارسنجی‌شده، هدرهای امنیتی پایه و حفاظت در برابر ارسال ناخواسته اطلاعات پزشکی به AI
- سیاست PostgreSQL RLS تهیه شده؛ اجرای FORCE RLS در پایگاه تولیدی هنوز نیازمند تأیید مستقل است

## خروجی جدید
- `POST /api/v1/privacy/requests`: ثبت درخواست access/rectification/erasure/restriction/portability فقط برای بیمار متعلق به Tenant جاری، با نقش admin
- `GET /api/v1/privacy/requests` و `GET /api/v1/privacy/requests/{id}`: فهرست و جزئیات حداقلی، محدود به Tenant و admin
- `POST /api/v1/privacy/requests/{id}/review`: گردش‌کار محدود:
  - `pending_identity → pending_legal_review` با تصمیم مدیر `identity_verified`
  - `pending_identity → rejected`
  - `pending_legal_review → legal_hold | closed_manual | rejected`
  - `legal_hold → closed_manual`
- رویدادهای تغییر وضعیت در جدول Audit موجود با شناسه درخواست ذخیره می‌شوند؛ متن پرونده/نام بیمار در این رویدادهای جدید ذخیره نمی‌شود.
- جدول `privacy_requests` و FKهای مرکب Tenant-aware؛ سیاست RLS پیش‌فرض ساخته می‌شود ولی **روی production خودکار فعال نمی‌گردد**.
- API عمداً **هیچ خروجی PHI صادر نمی‌کند، داده‌ای حذف نمی‌کند و هویت شخص را به‌تنهایی تأیید نمی‌کند**. تصمیم `identity_verified` ثبت تأیید انسانی است و بدون فرآیند عملیاتی مستقلی معتبر نیست.

## تست‌ها
```powershell
git fetch origin
git switch feature/section-28-healthcare-privacy
docker compose up -d --build
docker compose exec api alembic upgrade head
docker compose exec api pytest -q tests/test_section_28_privacy.py
```
تست شامل جداسازی Tenant، ممنوعیت نقش operator، تغییر وضعیت نامعتبر، حداقل‌سازی پاسخ، Audit و رد ورودی ناشناخته است. **اجرای تست هنوز در این جلسه تأیید نشده است.**

## موارد باقیمانده برای ادعای تکمیل تولیدی
1. احراز هویت مستقل درخواست‌کننده، رضایت/نمایندگی بیمار، پورتال امن درخواست شخصی و SLAهای مبتنی بر قانون محل
2. فرایند اجرایی تأییدشده استخراج، اصلاح، محدودیت پردازش، حذف و توقف نگهداری با کنترل legal hold، بکاپ و سیستم‌های ثالث
3. DPIA، مبنای قانونی پردازش، فهرست پردازشگران، انتقال برون‌مرزی، سیاست retention و رسیدگی به رخداد
4. KMS و vault و چرخش کلید عملیاتی، پشتیبان‌گیری رمزنگاری‌شده و تست بازیابی، آزمون ClamAV و اسکن آسیب‌پذیری
5. TLS خاتمه‌یافته و تست‌شده، WAF، CSP فرانت‌اند، DLP، ممیزی مستقل و تست نفوذ عملیاتی
6. ذخیره Audit غیرقابل‌دستکاری و سنجش جامع دسترسی PHI توسط کارکنان، بیمار و سرویس‌ها
7. اجرای PostgreSQL FORCE RLS در معماری نهایی و آزمون نفوذ cross-tenant

**معیار پذیرش:** گزارش‌های مستقل امنیت/حریم خصوصی و آزمون restore، اسکن فایل، نشت لاگ، کنترل دسترسی و گردش‌کار حقوق داده، پیش از فعال‌سازی بیماران واقعی.
