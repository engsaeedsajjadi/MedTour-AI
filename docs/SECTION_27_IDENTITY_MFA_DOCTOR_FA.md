# بخش ۲۷ — هویت، MFA کارکنان و دسترسی پرونده‌ای پزشک

## وضعیت
پیاده‌سازی MFA اختیاری کارکنان و نقش محدود پزشک برای پیش‌نمایش اداری در محیط Alpha. **هویت حرفه‌ای پزشک، عضویت در نظام پزشکی، ورود با Passkey/WebAuthn، چرخه بازیابی حساب و مجوز واقعی دسترسی به PHI هنوز مستقل ارزیابی نشده‌اند.**

### MFA
- `POST /api/v1/identity/mfa/setup`: از نشست کارکنان صادر می‌شود؛ کلید تصادفی TOTP ایجاد، با AES-256-GCM و AAD شناسه Tenant و User رمز می‌شود؛ OTP URI و Secret فقط در پاسخ شروع ثبت‌نام ظاهر می‌شوند.
- `POST /api/v1/identity/mfa/activate`: فعال‌سازی پس از تأیید کد شش‌رقمی RFC 6238 و ثبت شمارنده آخرین استفاده؛ محدودیت تلاش برای فعال‌سازی؛ چرخش و ابطال همه Refresh Sessionهای قبلی.
- `GET /api/v1/identity/mfa/status`: فقط فعال/غیرفعال بودن ثبت‌نام خود فرد، بدون افشای Secret.
- `POST /api/v1/auth/login` و مسیر principal-scoped Login بخش ۲۶ هر دو برای حساب‌هایی که MFA فعال دارند، `totp_code` می‌خواهند. استفاده دوباره از همان بازه کد TOTP رد می‌شود.
- `STAFF_MFA_ENCRYPTION_KEY`: کلید مستقل AES به طول ۳۲ بایت، Base64URL؛ **در GitHub یا فرانت‌اند قرار ندهید**. مدیریت امن Secrets، بازیابی اضطراری با احراز هویت مستقل، لاگ امنیتی و چرخش کلید باید پیش از تولید واقعی طراحی شود.
- MFA هنوز برای کاربران تازه **به‌صورت اجباری سازمانی** فعال نشده است؛ **این مرحله به‌معنای MFA تولیدی یا مقاومت قطعی در برابر فیشینگ نیست**. نشست‌های Access قبلی حداکثر تا انقضای فعلی می‌توانند زنده بمانند؛ برای سیاست سخت‌گیرانه باید کنترل `auth_time` و `mfa_at` در هر Request همراه با Session Revocation کامل اضافه شود.

### پزشک
- نقش `doctor` فقط به مسیرهای `/api/v1/identity/doctor/cases` و `/api/v1/identity/doctor/cases/{id}` دسترسی دارد و فقط شناسه پرونده، تخصص و وضعیت **غیربالینی** برمی‌گردد.
- تخصیص توسط مدیر همان Tenant از `POST /api/v1/identity/doctor-grants/{case_id}` با `user_id` فعال و نقش `doctor` انجام می‌شود و با `DELETE /api/v1/identity/doctor-grants/{case_id}/{user_id}` فوراً در Queryهای بعدی لغو می‌شود.
- دسترسی عمومی به Patients/Medical Documents و تصمیم تشخیص یا درمان برای نقش پزشک در این قابلیت فعال نیست. یک grant برای Tenant دیگر یا پرونده تخصیص‌نیافته `404` می‌دهد.
- این role **به معنی احراز هویت پزشک یا اجازه داده بالینی نیست**؛ برای نسخه تجاری باید مجوز حرفه‌ای، احراز هویت قوی‌تر، رضایت مخصوص و سطح دسترسی مورد پرونده‌ای مستند اضافه شود.

### پایگاه‌داده
Migration `a27e793f06b1`، جداول `staff_mfa` و `doctor_case_grants` را همراه با Unique Tenant-ID، چهار FK مرکب Tenant-aware و سیاست `mt26_principal_isolation` نصب می‌کند. مانند بخش ۲۶، RLS روی DB اصلی **به‌صورت خودکار فعال نمی‌شود**، ولی Probeهای PostgreSQL آزمایشی با FORCE RLS آن را اعتبارسنجی می‌کنند.

### تست
فایل `backend/tests/test_section_27_identity.py`: فعال‌سازی و ورود دومرحله‌ای، رد کد اشتباه و Replay، عدم افشای کلید، تفکیک Tenant، تخصیص و لغو دسترسی پرونده پزشک. CI با PostgreSQL 17 / Redis 7 و Next.js/TypeScript نیز بررسی می‌شود.

## راه‌اندازی در محیط توسعه
از DB نسخه پشتیبان بگیرید و در Secret Manager یا `.env` محلی یک کلید تصادفی ۳۲ بایتی Base64URL تعیین کنید. فعال‌سازی این متغیر روی سیستم، MFA هیچ حسابی را به‌صورت خودکار اجباری نمی‌کند.

```powershell
git pull --ff-only origin main
docker compose up -d --build
docker compose exec api alembic upgrade head
```

**هشدار:** برای بیماران واقعی یا استقرار Production از این قابلیت استفاده نکنید؛ امنیت و هویت رسمی باید به‌صورت مستقل تأیید شوند.
