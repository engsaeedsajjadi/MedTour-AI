# بخش ۲۳ — CMS سازمانی: نسخه‌بندی و تأییدهای مستقل

**وضعیت:** زیرساخت داخلی گردش‌کار و تاریخچه نسخه‌ها پیاده‌سازی شده است؛ *تأیید مستقل مدارک صلاحیت پزشک، مترجم یا مشاور حقوقی توسط نهاد بیرونی انجام نشده است.* این سامانه همچنان Alpha با داده‌های ساختگی است و برای دریافت/انتشار اطلاعات واقعی پزشکی بیماران مناسب نیست.

## مسئله پیشین و تغییر امنیتی

قبل از این بخش، `PATCH /api/v1/cms/pages/{id}/publish` تنها با نقش admin قادر بود پیش‌نویس را مستقیماً منتشر کند. اکنون این مسیر نیز به کنترل **سه بازبینی مستقل** متصل شده است؛ ویرایش مستقیم قدیمی `PATCH /api/v1/cms/public-site/drafts/{id}` با **409** بسته می‌شود.

**اثر Migration بر محتوای واقعی قبلی:** Migration `a23e674c5b20` (فرزند `a21c493b5e70`) تمام متن‌های CMS موجود را به‌صورت نسخه ۱ ثبت و **صفحات منتشرشده قبلی را به پیش‌نویس تبدیل می‌کند** تا بدون بازبینی جدید عمومی باقی نمانند. پیش از استقرار از DB پشتیبان بگیرید و برای انتشار دوباره هر صفحه، بازبینی سه‌گانه انجام دهید. برگشت Migration عمداً منتشرسازی قدیمی را به‌صورت خودکار فعال نمی‌کند.

## مدل داده

- `content_pages.published_version_no`: شماره نسخه‌ای که آخرین بار پس از مرور تخصصی عمومی شده است؛ `NULL` یعنی صفحه حق انتشار ندارد.
- `cms_versions`: هر نسخه دارای `tenant_id`، `page_id`، `version_no` یکتا، متن و عنوان Snapshot (از طریق API تغییرناپذیر)، SHA-256 متن، نویسنده، دلیل تغییر و حالت.
- `cms_reviews`: برای هر نسخه **حداکثر یک رأی در هر مرحله** `translation` / `medical` / `legal`، با `reviewer_id`، تصمیم `approved` یا `rejected` و مرجع سند غیرحساس.
- `cms_workflow_events` + `audit_events`: تاریخچه ایجاد نسخه، ارسال، رد/تأیید، انتشار و از انتشار خارج‌کردن، شامل عامل و زمان.

## تفکیک مسئولیت‌ها

| نقش | مجوز |
|---|---|
| `admin` | ایجاد صفحه، حساب بازبین، مدیریت CMS، انتشار نسخه‌ای که سه رأی معتبر داخلی دارد، لغو انتشار |
| `cms_editor` | مشاهده، ساخت نسخه جدید و ارسال نسخه‌های خودش برای بازبینی |
| `cms_translator` | مشاهده متن عمومی و تصمیم تنها در مرحله ترجمه |
| `cms_medical_reviewer` | مشاهده متن عمومی و تصمیم تنها در مرحله ادعاهای پزشکی |
| `cms_legal_reviewer` | مشاهده متن عمومی و تصمیم تنها در مرحله حقوقی |

حساب‌های بازبین توسط مدیر از `POST /api/v1/cms/workflow/reviewers` یا صفحه `/cms-workflow` ایجاد می‌شوند. **این نقش‌ها صرفاً سطح دسترسی داخلی‌اند و به معنی احراز رسمی مدرک یا صلاحیت حرفه‌ای نیستند.** تأیید نویسنده از متن خودش ممنوع است. هر مرحله باید توسط **بازیگر جداگانه** انجام شود. مدیر پس از هر سه تأیید می‌تواند نسخه را منتشر کند، مشروط بر اینکه خودش هیچ‌کدام از سه بازبین آن نسخه نباشد.

## فرایند

۱. مدیر از `/cms` صفحه جدید می‌سازد یا با Bootstrap پنج‌زبانه، ۴۰ صفحه **پیش‌نویس** ایجاد می‌کند.

۲. صفحه `/cms-workflow` تاریخچه Snapshotها و مقایسه نسخه‌ها را نشان می‌دهد. ویرایش، یک `cms_versions` جدید می‌سازد؛ باید `expected_version` مطابق آخرین شماره باشد، وگرنه **409** برای جلوگیری از ذخیره هم‌زمان نادرست.

۳. نسخه جدید از `draft` به `in_review` فرستاده می‌شود.

۴. سه بازبین با حساب‌های مختلف و نقش خاص خود `approved` می‌دهند. رد یک مرحله، نسخه را `rejected` و انتشار را ممنوع می‌کند.

۵. سه تأیید برای **همان نسخه** لازم است؛ نسخه `ready` می‌شود. تأییدهای قدیمی به نسخه جدید منتقل نمی‌شوند.

۶. مدیر `POST /api/v1/cms/workflow/pages/{id}/publish` را اجرا می‌کند. فقط همین‌جا Snapshot جدید به `content_pages.title/body` منتقل و `published_version_no` به‌روزرسانی می‌شود. اگر قبلاً نسخه‌ای منتشر شده باشد، هنگام ویرایش بعدی همان نسخه قبلی همچنان برای بازدیدکنندگان قابل مشاهده می‌ماند تا نسخه جدید آماده و منتشر شود.

۷. بازگردانی نسخه قدیمی (`.../versions/{version_id}/restore`) فقط یک **نسخه تازه** ایجاد می‌کند؛ هیچ محتوای بازیابی‌شده‌ای بدون سه بررسی مجدد خودکار منتشر نمی‌شود.

۸. لغو انتشار همچنان از مسیر بخش ۲۲ انجام می‌شود، ولی `published_version_no` پاک و نسخه منتشرشده `withdrawn` می‌شود. برای انتشار مجدد باید نسخه تازه‌ای ایجاد و بررسی شود.

## API جدید

- `GET /api/v1/cms/workflow/pages` — خلاصه آخرین نسخه و وضعیت سه مرحله
- `GET /api/v1/cms/workflow/pages/{id}/versions` — Snapshotهای نسخه‌ای برای اعضای مجاز همان Tenant
- `POST /api/v1/cms/workflow/pages/{id}/versions` — ایجاد نسخه با `title`، `body`، `expected_version`، `reason`
- `POST /api/v1/cms/workflow/pages/{id}/submit` — ثبت درخواست سه بازبینی
- `POST /api/v1/cms/workflow/pages/{id}/reviews/{translation|medical|legal}` — نظر بازبین واجد نقش، مرجع اداری و تصمیم
- `POST /api/v1/cms/workflow/pages/{id}/publish` — انتشار نسخه دارای سه رأی معتبر، فقط admin
- `POST /api/v1/cms/workflow/pages/{id}/versions/{version_id}/restore` — نسخه جدید از Snapshot تاریخی
- `GET /api/v1/cms/workflow/pages/{id}/history` — تاریخچه حسابرسی

## راه‌اندازی

```powershell
git pull origin main
docker compose up -d --build
docker compose exec api alembic upgrade head
```

به `http://localhost:3000/cms-workflow` مراجعه کنید. حساب‌های داخلی بازبین را از پنل مدیر با گذرواژه قوی بسازید و هر کدام را با نقش خودش وارد کنید. گردش‌کار پیش از مرحله انتشار نیازمند **سه شخص متمایز** است.
