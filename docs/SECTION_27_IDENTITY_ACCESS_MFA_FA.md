# بخش ۲۷ — احراز هویت، MFA و مدیریت دسترسی MedTour AI

**وضعیت:** TOTP اختیاری برای حساب‌های کارکنان، نسخه‌بندی نشست، مدیریت تغییر رمز و تعلیق/تغییر نقش، و حفظ کنترل تفکیک‌شده پرتال پزشک در محیط **Alpha مصنوعی** پیاده‌سازی شده است. این پیاده‌سازی به‌تنهایی تأیید هویت رسمی، احراز هویت مبتنی بر Passkey/WebAuthn یا مجوز Production پزشکی نیست.

## تغییرات امنیتی

- مهاجرت `a27f159d6821` فیلد `users.auth_version` و جداول `staff_totp` و `staff_mfa_challenges` را با کلیدهای Tenant و قیود مرجع به User می‌سازد. Policy قبلی `mt26_principal_isolation` نیز برای جداول جدید روی PostgreSQL **ایجاد می‌شود ولی RLS عملیاتی فعال نمی‌شود**. اجرا با دیتابیس مصنوعی PostgreSQL 17 تست می‌شود.
- TOTP با کلید تصادفی ۱۶۰ بیت (SHA-1 مطابق TOTP استاندارد، گام ۳۰ ثانیه، ۶ رقم و بازه قابل‌قبول ±۱ گام) ساخته می‌شود. Seed با AES-256-GCM و متغیر مستقل `MFA_ENCRYPTION_KEY` (Base64 URL-safe از ۳۲ بایت تصادفی) و Associated Data شامل Tenant و User در دیتابیس رمزگذاری می‌شود. برنامه **کلید رمزگذاری را تولید یا در دیتابیس ذخیره نمی‌کند**. نبودن کلید، فعال‌سازی یا ورود دارای MFA را با 503 رد می‌کند؛ هرگز به ورود تک‌مرحله‌ای برنمی‌گردد.
- راه‌اندازی عامل دوم از `POST /api/v1/auth/mfa/enroll`، با JWT فعال کاربر انجام می‌شود. URI و secret فقط در پاسخ اولیه به مالک همان حساب نمایش داده می‌شود، `Cache-Control: no-store` فعال است. باید ظرف ده دقیقه با TOTP صحیح در `.../mfa/confirm` تأیید شود. این عمل نسخه امنیتی حساب را افزایش و Refresh Tokenهای قبلی را باطل می‌کند و یک نشست جدید صادر می‌کند.
- **ورود کارکنان دارای MFA:** پس از رمز معتبر، `POST /api/v1/auth/login` فقط HTTP 202، `mfa_required` و Challenge تصادفی SHA-256‌شده در دیتابیس می‌دهد. تا قبل از `POST /api/v1/auth/mfa/verify` با کد معتبر هیچ Access/Refresh صادر نمی‌شود؛ Challenge فقط پنج دقیقه عمر و پنج تلاش دارد و بعد از مصرف/دورزدن/انقضا رد می‌شود. در همان حساب از کد TOTP استفاده‌شده دوباره نمی‌توان استفاده کرد. کد مورد استفاده در فعال‌سازی، برای ورود فوری در همان بازه ۳۰ ثانیه‌ای قابل تکرار نیست.
- `users.auth_version` داخل JWT امضاشده قرار می‌گیرد و `current_user` آن را با نسخه حال حاضر حساب تطبیق می‌دهد. تغییر گذرواژه، غیرفعال‌سازی/فعال‌سازی یا تغییر نقش غیرمدیر، نسخه را افزایش می‌دهد و همه خانواده‌های Refresh فعال را می‌بندد. نقش مدیر با API ساده به فرد جدید اعطا/حذف نمی‌شود؛ این اقدام به سیاست مستقل مالک سازمان نیاز دارد.
- نقش پزشک و دسترسی به پرتال به هم مرتبط **ولی یکسان نیستند**. حساب دارای نقش `physician` برای ورود عمومی مجاز است، اما دسترسی `/api/v1/physician-management/portal/*` تنها پس از ثبت `PhysicianAccount` فعال همان Tenant و اعتبارنامه داخلی معتبر امکان‌پذیر است. بازبینی بالینی دیگری که مجوز و تخصیص مستقل دارد، نباید با ایجاد اجبار لینک پرتال شکسته شود. اعتبار حرفه‌ای پزشک **از نهاد صدور مجوز خارجی بررسی نشده**.
- مسیر آزمایشی strict tenant Gateway بخش ۲۶، برای حساب‌هایی که MFA فعال دارند در `StagedPreAuthService` و `StagedTenantCredentialTransactions` **Fail Closed** باقی می‌ماند. هنوز چالش دوم را با مسیر pre-auth دارای نقش مستقل PostgreSQL اجرا نمی‌کند؛ به‌هیچ‌وجه نباید از `main.login` یا Refresh Token قدیمی برای دورزدن آن استفاده شود.

## API و رابط کاربری

| درخواست | مسیر | شرح |
| --- | --- | --- |
| GET | `/api/v1/auth/mfa/status` | وضعیت حساب بدون نمایش Secret |
| POST | `/api/v1/auth/mfa/enroll` | Seed رمزگذاری‌شده و URI نمایش موقت به مالک |
| POST | `/api/v1/auth/mfa/confirm` | تأیید و ابطال نشست‌های قبلی |
| POST | `/api/v1/auth/mfa/verify` | مصرف Challenge پس از Password |
| POST | `/api/v1/auth/password/change` | تغییر رمز با ارائه رمز قبلی و خروج از نشست‌ها |
| GET | `/api/v1/auth/staff` | فهرست نقش‌ها و وضعیت کارکنان همان Tenant |
| PUT | `/api/v1/auth/staff/{id}/active` | فعال/غیرفعال‌سازی با ابطال نشست |
| PUT | `/api/v1/auth/staff/{id}/role` | جابه‌جایی نقش غیرمدیر، بدون ارتقای مدیر |

ورود دومرحله‌ای در `/login` و تنظیمات امنیتی فارسی در `/account-security` در منو قرار دارد. کلید TOTP در SessionStorage ذخیره نمی‌شود؛ فقط Access/Refresh پس از MFA نگهداری می‌شوند. نگهداری JWT در SessionStorage **امنیت معادل کوکی HttpOnly ندارد** و برای Production به طراحی ضد XSS و نشست سمت سرور نیاز است.

### پیکربندی

در محیط توسعه با کلید واقعی تصادفی ۳۲بایتی و خارج از Git:

```powershell
# اجرا در PowerShell محلی؛ خروجی Base64 را در Secret Store نگهداری کنید.
[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

`MFA_ENCRYPTION_KEY` باید در Backend فراهم و در همه Replicaها یکسان باشد. **بدون این کلید حسابی که MFA دارد قادر به ورود نخواهد بود**. روی محیط دارای اطلاعات مهم، قبل از Migration و چرخش کلید از دیتابیس و Secret Store پشتیبان بازیابی‌پذیر بگیرید.

```powershell
git pull --ff-only origin main
docker compose up -d --build
docker compose exec api alembic upgrade head
```

این دستورات RLS موجود را روی دیتابیس عملیاتی فعال نمی‌کنند. روی داده واقعی پزشکی استفاده نشود.

## آزمون و معیارهای پذیرش

`backend/tests/test_section_27_identity_mfa.py`: راه‌اندازی و رمزگذاری Seed، چالش فقط پس از رمز صحیح، عدم صدور JWT قبل از عامل دوم، پنج تلاش، Replay، جداسازی Tenant، نبود کلید AES، تغییر رمز، تعلیق کارکنان، و مرز پرتال پزشک.

GitHub Actions شامل Pytest و مهاجرت PostgreSQL17/Redis7 با RLS آزمایشی است. نتیجه واقعی هر Run باید قبل از ادغام بررسی شود.

## محدودیت‌های باقی‌مانده پیش از Production

احراز هویت مقاوم به فیشینگ (Passkeys/WebAuthn)، بازیابی عامل دوم با فرآیند تأیید هویت مستقل و دومرحله‌ای، سیاست MFA اجباری برای مدیران و نقش‌های حساس پس از Enrollment کنترل‌شده، چرخه عمر Secret در Secret Manager، اطلاع‌رسانی امنیتی، گزارش نشست‌ها و ابطال از چند دستگاه، محافظت CSRF/XSS/HttpOnly، Provider SSO/OIDC/SAML، سیاست مستقل تجاری ایجاد مدیر، PenTest و ممیزی حریم خصوصی. **هیچ Reset خودکار یا بک‌آپ‌کد ناامن برای MFA عرضه نشده است.**
