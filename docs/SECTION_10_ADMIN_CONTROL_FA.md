# MedTour AI — بخش ۱۰: مرکز کنترل مدیریتی

**تاریخ:** 2026-10-23. **نسخه:** Alpha توسعه، فقط اطلاعات ساختگی؛ استفاده با بیمار واقعی مجاز نیست.

## خروجی اجرایی

- **داشبورد مدیریتی مستقل:** `/admin-center` در رابط فارسی RTL. دسترسی تمام APIهای جدید فقط برای حساب `admin` سازمان است؛ اپراتور، حساب پزشک و مدیر سازمان دیگر اجازه دسترسی ندارند.
- **آمار واقعی پایگاه داده:** `GET /api/v1/admin-center/summary` شمار بیماران، پرونده‌ها، کاربران فعال، پیگیری‌های باز/معوق، خدمات معلق، پیش‌فاکتورهای پیش‌نویس، مکالمات ارجاع‌شده به انسان، هشدارهای پذیرش، ترجمه‌های نیازمند تأیید و پیام‌های منتظر تأیید انسانی را با `tenant_id` برمی‌گرداند. این اعداد تنها **وضعیت رکوردهای داخلی** هستند؛ صدور ویزا، رزرو بیمارستان، دریافت پیام یا فعالیت تأییدشده ارائه‌دهنده را اثبات نمی‌کنند.
- **صف اولویت‌دار کارهای اداری:** `GET /api/v1/admin-center/queue` هشدار پذیرش، پذیرش نیازمند بازبینی انسانی، پیگیری معوق، خدمات معلق، پیش‌فاکتور پیش‌نویس و گفت‌وگوهای ارجاع‌شده را فهرست می‌کند. صف فقط شناسه، وضعیت، اولویت و مقصد گردش‌کار را نمایش می‌دهد. هشدار اورژانس در این صفحه **هیچ‌وقت خودکار تأیید/رفع نمی‌شود**؛ مرور عبارات فقط هشدار واژه‌ای است و تریاژ پزشکی نیست. جست‌وجوی رکوردها محدود به آخرین ۲۵۰ رکورد هر دسته است؛ نتیجه API صراحتاً **غیرجامع** اعلام می‌شود.
- **جست‌وجوی پیشرفته و محدود به سازمان:** `GET /api/v1/admin-center/search` با عبارت ۳ تا ۸۰ کاراکتر و فیلتر بیماران، پرونده‌ها و عملیات، شناسه‌ها، نام بیمار آزمایشی و برچسب/وضعیت اداری را برمی‌گرداند. از بازگرداندن متن شکایت پزشکی، مدارک، اطلاعات تماس، یادداشت‌های خدمات یا کلیدهای محرمانه جلوگیری می‌کند؛ حداکثر ۵۰ نتیجه از هر درخواست. `%/_` در جست‌وجوی LIKE escape می‌شوند.
- **نمای اداری پرونده:** `GET /api/v1/admin-center/cases/{case_id}/overview` وضعیت، شناسه‌ها، مسئول، رضایت فعال برای پذیرش/ارتباطات و تعداد محدود وظایف/خدمات معلق را نشان می‌دهد؛ هیچ متن یا نتیجه بالینی را بازنمی‌گرداند.
- **کنترل دسترسی کارکنان:** `POST /api/v1/admin-center/staff/{id}/deactivate` فقط برای مدیر است. غیرفعال‌سازی خود مدیر، افراد دارای پرونده/بیمار/گفت‌وگو/خدمت/پیگیری یا انتساب فعال پزشک، مسدود است. با غیرفعال‌سازی موفق، Audit ثبت می‌شود و کنترل `current_user` باعث رد Tokenهای قدیمی از درخواست بعدی خواهد شد. واگذاری/بستن کارها باید **به‌صورت انسانی** در ماژول موجود انجام شود. هیچ حذف فیزیکی کاربر انجام نمی‌شود.
- **بدون Migration جدید:** کد از مدل‌های سازمان‌محور موجود استفاده می‌کند. پرونده‌ها، عملیات، پذیرش، پیگیری‌های CRM و پیام‌ها تغییر ساختاری ندارند. گزارش عملگرهایی که به تأیید واقعی خارجی نیاز دارند به صفحات موجود هدایت می‌شود، نه به اکشن یک‌کلیکی یا تأیید خودکار.

## شواهد آزمون

`backend/tests/test_section_10_admin_center.py`: کنترل نقش مدیر، ایزوله‌سازی Tenant، آمار بر اساس وضعیت واقعی، جست‌وجوی بدون PHI، اولویت‌دهی هشدار فوری، صف پیگیری معوق و پیش‌فاکتور/عملیات، نمای پرونده، جلوگیری از غیرفعال‌سازی خود مدیر، جلوگیری از غیرفعال‌سازی حساب دارای کار فعال، لغو Token کارمند و Audit.

GitHub Actions باید تمام تست‌های Backend با داده ساختگی، TypeScript/Next.js و تست PostgreSQL 17 + Redis 7 را پاس کند.

## بخش‌هایی که برای Enterprise عملیاتی باز می‌مانند

مجوز پردازش PHI، احراز هویت چندعاملی و قوی بیمار/کارکنان، پایگاه داده PostgreSQL RLS عملیاتی، لاگ غیرقابل‌تغییر و SIEM، مدیریت موارد بیش از محدوده صف، کنترل دسترسی موردی در هر سازمان، قوانین حریم خصوصی/نگهداری داده در کشورهای هدف، سیاست واقعی SLA و روال پاسخ‌گویی اورژانس، تست میدانی ارائه‌دهندگان و نفوذسنجی مستقل.

**وضعیت پذیرش بخش ۱۰:** مرکز کنترل مدیریت و جست‌وجو/صف/کنترل دسترسی در سطح نرم‌افزار توسعه پیاده‌سازی شده است؛ مدرک Production Enterprise یا صلاحیت پزشکی صادر نشده است.
